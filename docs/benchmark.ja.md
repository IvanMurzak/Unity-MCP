# ベンチマーク: Unity エディターでのコンパクトなツール

[README](README.ja.md) に戻る。

AI Game Developer は、操作ごとに 1 つのツールを用意する代わりに、エディターのデータに対するクエリ言語 **RQL** の上に作られた少数のコンパクトなツールをエージェントに提供します。実際の Unity エディターで、両方のツールカタログを使って同じタスクを実行しました。エージェントが解いたタスクの数は同じでしたが、**プロンプトトークンは約 5 分の 1** で、ターン数とツール呼び出しも少なく、各タスクをより速く終えました。サンドボックスのゲームワールドで行った、より大規模な 2 つ目のテストでも同じ傾向が見られます。

## 主な数値（Unity エディター）

| 5.3× | −31% | −39% | 59 / 60 |
| :---: | :---: | :---: | :---: |
| タスクあたりのプロンプトトークン削減 | タスクあたりのツール呼び出し | タスクあたりの所要時間 | 解いたタスク（両カタログとも） |

## Unity エディターでの結果

| 指標 | 操作ごとのツール | RQL ツール |
| --- | ---: | ---: |
| 解いたタスク（タスクのチェックに合格し、意図しない変更なし） | 59 / 60 | 59 / 60 |
| タスクあたりのプロンプトトークン | 138,272 | **26,013** |
| タスクあたりの補完トークン | 673 | **306** |
| タスクあたりのモデルのターン数 | 5.4 | **4.1** |
| タスクあたりのツール呼び出し / エラー | 5.5 / 0.5 | **3.8 / 0.2** |
| タスクあたりのツール結果のサイズ（文字数） | 6,273 | **657** |
| 毎リクエストで送られるツール定義（文字数） | 93,194 | **22,439** |
| タスクあたりの実時間 | 8.8 s | **5.4 s** |
| タスクあたりのツール実行時間 | 169 ms | **42 ms** |
| タスクあたりのコスト | 1× | **約 ⅓** |

**安くなる理由。** 差の大部分は 2 か所から生まれます。エージェントが毎リクエストで受け取るツール定義が 4.2 分の 1、ツール結果が 9.5 分の 1 になります。一括処理やクエリのタスクでは、操作ごとのカタログは C# を書く方法に頼りました（全実行を通じて `script-execute` が 68 回、RQL では 7 回）。RQL では、エージェントは代わりにクエリを 1 つ書きます。

**対照実行。** 拡張機能の移行とコアの修正（所有者チェーンの元に戻す操作、アセットパス、`unity.find`、数値の書式）の後、RQL カタログは **60 / 60** のタスクを解き、タスクあたり 23,274 プロンプトトークン、3.4 回のツール呼び出し、4.8 s でした。

## サンドボックスのゲームワールドでの結果

RQL プロジェクトは、Unity の外で言語そのものを計測しています。生成されたゲームワールドと、RQL か単純なリフレクションツール（`find_objects`、JSON ダンプを返す `get_object`、`describe_type`、`set_value`、`call_method`）のどちらかを使うエージェントです。最もクリーンな検証では、すべての調整を凍結した後に書いた新しい 30 タスクを使い、1 回だけ、各タスク 3 回ずつ実行しました。

| 実行 | 解いたタスク | タスクあたりのトークン | タスクあたりのツール呼び出し | 成功 1 件あたりのコスト |
| --- | ---: | ---: | ---: | ---: |
| リフレクションツール、調整後に書いたタスク | 66.7% | 169,190 | 36.9 | 40× |
| RQL、調整後に書いたタスク | **100%** | **7,817** | **1.9** | **1×** |
| リフレクションツール、ホールドアウトタスク | 91.4% | 125,566 | 34.0 | 22× |
| RQL、ホールドアウトタスク | **100%** | **7,444** | **1.9** | **1×** |

リフレクションツールが失敗する主な原因は、「すべてを検索する」タスクでワールドをオブジェクト 1 つずつ読み取り、ステップを使い切ってしまうことです。

## 手法

**Unity エディター。** Unity-MCP 0.93.4（有効なすべてのツール、操作ごとに 1 つのツール: `gameobject-*`、`assets-*`、`scene-*`、`object-*`、`console-get-logs`、`script-execute`、`tests-run`、…）と RQL カタログ（`rql-query`、`rql-mutate`、`rql-schema`、`script-execute`、`tests-run`、`screenshot-isolated`、`unity-tool-list`）を比較して計測しました。両方とも同じハーネス、シーン、モデルを使用: `deepseek-flash`、推論オフ、temperature 0。20 タスク × 3 回の実行、Unity 6000.6.4f1。各条件には MCP クライアントが見るとおりのツールを、それぞれの名前、説明、入力スキーマのまま渡し、プラグイン経由で呼び出しました。タスクは、そのチェックに合格し、シーン内のほかに何も変わっていない場合にのみ合格とします。

**サンドボックス。** 両方のツール群で、タスク、採点器、モデル、予算は同じで、違うのはツールだけです。モデルは DeepSeek V4.1-Flash、タスクあたり最大 12 ステップ、各タスク 3 回の実行。非公開の採点器が期待される答えを独立に計算し、変更系のタスクは意図しない変更があれば失敗とします。ホールドアウトタスクは調整に一度も使っておらず、2 つ目のタスクセットは調整の凍結後に書いて 1 回だけ実行しました。

## 注意点

- **1 つのモデルファミリー。** どちらのテストも DeepSeek のモデルを使用しました。ほかのモデルでは数値が異なる可能性があります。
- **計測したバージョン。** Unity エディターの数値は、1 つのシーンと 1 つの Unity バージョンで Unity-MCP 0.93.4 と RQL カタログを比較したものです。ツールとモデルは時間とともに変わります。
- **サンプルが小さい。** エディターでは条件ごとに 60 回の実行、上記のサンドボックスの結果では条件ごとに 81〜90 回の実行です。
- **同じ作者。** RQL のタスクとサンドボックスは、この言語の作者が設計しました。ホールドアウトタスクと調整後に書いたタスクセットはこの偏りを減らしますが、なくすものではありません。
- **コストは比率。** プロンプトキャッシュのため、コストはほかのトラフィックにも一部左右されます。トークン数とツール呼び出しのほうが安定した指標です。
