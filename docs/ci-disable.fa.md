# غیرفعال کردن Unity-MCP در CI

در core نسخه **1.6.2** و افزونه‌های رسمی نسخه **2.1.1** معرفی شده است.

این گزینه‌های انصراف مستقل، manifest مربوط به UPM را بدون تغییر می‌گذارند. هیچ‌کدام برای `-batchmode` یا `-runTests` به‌طور خودکار
فعال نمی‌شوند: نشست‌های MCP بدون رابط گرافیکی و تست‌های خود MCP همچنان به پلاگین نیاز دارند.

## گزینه 1: صرف‌نظر از مقداردهی اولیه (توصیه‌شده برای تست‌های معمولی CI)

متغیر محیطی فرایند را **پیش از اجرای Unity** تنظیم کنید:

</div>

```bash
UNITY_MCP_DISABLE=1 "$UNITY_EDITOR" -batchmode -nographics \
  -projectPath "$PROJECT_PATH" -runTests -testPlatform PlayMode \
  -testResults "$PROJECT_PATH/test-results.xml" -logFile -
```

<div dir="rtl">

در GitHub Actions، `UNITY_MCP_DISABLE: '1'` را در نگاشت `env` مرحله‌ای که Unity را اجرا می‌کند قرار دهید.
برای یک runner مبتنی بر Docker، آن را صراحتاً به کانتینر Unity منتقل کنید، برای مثال
`docker run --env UNITY_MCP_DISABLE=1 ...`. تنظیم آن فقط روی میزبان لزوماً
آن را به کانتینر یک action منتقل نمی‌کند.

‏`1` و `true` (بدون حساسیت به بزرگی و کوچکی حروف، با نادیده گرفتن فاصله‌های اطراف) MCP را غیرفعال می‌کنند. حالت تنظیم‌نشده، `0`،
‏`false` و مقادیر ناشناخته رفتار عادی را حفظ می‌کنند. پس از تغییر آن Unity را دوباره اجرا کنید.
این یک بازنویسی در سطح فرایند است و در تنظیمات پروژه ذخیره نمی‌شود.

‏MCP از راه‌اندازی، ثبت ابزارها، callbackهای test-runner، دانلود/اجرای سرور در پس‌زمینه،
resolve کردن وابستگی‌های NuGet، جمع‌آوری لاگ و hookهای editor/PlayMode صرف‌نظر می‌کند. سورس‌های آن همچنان کامپایل می‌شوند
و assemblyها همچنان می‌توانند بارگذاری شوند. بنابراین وابستگی‌های موجود پروژه باید معتبر باشند؛ این حالت
راه‌حلی برای DLLهای غایب یا خطاهای کامپایل نیست. مقداردهی اولیه صریح runtime در حالت
غیرفعال یک استثنا گزارش می‌کند. برای jobهایی که عمداً MCP را آزمایش می‌کنند، این متغیر را حذف کنید.

## گزینه 2: خارج کردن assemblyهای سورس MCP از کامپایل

‏**`UNITY_MCP_EXCLUDE_FROM_COMPILATION`** را به **Scripting Define Symbols** یونیتی در
**Project Settings > Player > Other Settings** اضافه کنید، برای هر build target که jobهای CI شما استفاده می‌کنند.
نمادهای دیگر را حفظ کنید. این یک نماد اسکریپت‌نویسی است، **نه یک متغیر محیطی**.

برای CI، فایل `ProjectSettings/ProjectSettings.asset` حاصل را پیش از اجرای Unity آماده کنید
(برای مثال، از یک نسخه تنظیمات مخصوص CI استفاده کنید). اگر توسعه‌دهندگان به MCP نیاز دارند، تنظیمات توسعه معمولی را
بدون این نماد نگه دارید. آن را از یک `-executeMethod` در همان اجرای تست تنظیم نکنید:
این کار پس از اولین کامپایل اتفاق می‌افتد و تغییر defineها یک کامپایل دیگر را راه می‌اندازد.

همه assemblyهای بسته core (شامل dependency resolver، runtime، editor، ماژول‌های RQL
و تست‌های بسته)، به‌علاوه assemblyهای به‌روزشده افزونه‌های رسمی، از constraint منفی assembly
‏`!UNITY_MCP_EXCLUDE_FROM_COMPILATION` استفاده می‌کنند. این نماد همه آن assemblyها را با هم خارج می‌کند.
هر افزونه MCP نصب‌شده را هم به نسخه‌ای که این constraint را دارد به‌روز کنید؛ نسخه‌های قدیمی‌تر
و افزونه‌های شخص ثالث ممکن است همچنان به assemblyهای core خارج‌شده ارجاع دهند. کد سفارشی که
به نوع‌های MCP ارجاع می‌دهد باید از constraintهای متناظر یا `#if !UNITY_MCP_EXCLUDE_FROM_COMPILATION` استفاده کند.

این کار assemblyهای سورس C# مربوط به MCP را خارج می‌کند. بسته‌های UPM را حذف نصب نمی‌کند، assetهای import‌شده را حذف نمی‌کند،
و DLLهای از پیش کامپایل‌شده‌ای را که با بسته‌های دیگر مشترک هستند حذف یا غیرفعال نمی‌کند. حذف این نماد کامپایل عادی را
بازمی‌گرداند. جابه‌جایی بین حالت‌ها می‌تواند کش کامپایل Unity را نامعتبر کند؛ برای jobهای خارج‌شده و عادی کلیدهای کش CI
جداگانه نگه دارید. متغیر محیطی گزینه 1 در این حالت لازم نیست.
