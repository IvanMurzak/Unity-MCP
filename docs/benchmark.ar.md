# اختبار الأداء: أدوات مدمجة في محرر Unity

العودة إلى [README](README.ar.md).

‏يمنح AI Game Developer الوكيل بضع أدوات مدمجة مبنية على **RQL**، وهي لغة استعلام فوق بيانات المحرر، بدلًا من أداة واحدة لكل إجراء. شغّلنا المهام نفسها في محرر Unity الحقيقي مع كلا فهرسي الأدوات. حلّ الوكيل العدد نفسه من المهام مع **رموز موجّه (prompt tokens) أقل بنحو 5 أضعاف**، وجولات أقل واستدعاءات أدوات أقل، وأنهى كل مهمة أسرع. ويُظهر اختبار ثانٍ أكبر على عالم لعبة تجريبي (sandbox) النمط نفسه.

## نتائج محرر Unity

| المقياس | أدوات لكل إجراء | أدوات RQL |
| --- | ---: | ---: |
| المهام المحلولة (نجح فحص المهمة، دون أي تغيير غير مقصود) | ⁦59 / 60⁩ | ⁦59 / 60⁩ |
| رموز الموجّه لكل مهمة | ⁦138,272⁩ | **⁦26,013⁩** |
| رموز الإكمال (completion tokens) لكل مهمة | ⁦673⁩ | **⁦306⁩** |
| جولات النموذج لكل مهمة | ⁦5.4⁩ | **⁦4.1⁩** |
| استدعاءات الأدوات / الأخطاء لكل مهمة | ⁦5.5 / 0.5⁩ | **⁦3.8 / 0.2⁩** |
| حجم نتائج الأدوات لكل مهمة (محارف) | ⁦6,273⁩ | **⁦657⁩** |
| تعريفات الأدوات المرسلة مع كل طلب (محارف) | ⁦93,194⁩ | **⁦22,439⁩** |
| الوقت الفعلي لكل مهمة | ⁦8.8 s⁩ | **⁦5.4 s⁩** |

| التكلفة لكل مهمة | ⁦1×⁩ | **نحو ⅓** |

‏**لماذا هو أرخص.** يأتي معظم الفارق من موضعين: تعريفات الأدوات التي يتلقاها الوكيل مع كل طلب أصغر بمقدار 4.2×، ونتائج الأدوات أصغر بمقدار 9.5×. في مهام العمليات المجمّعة والاستعلام لجأ فهرس الأدوات لكل إجراء إلى كتابة شيفرة C# ‏(`script-execute` ‏68 مرة عبر كل التشغيلات، مقابل 7 مرات مع RQL)؛ أما مع RQL فيكتب الوكيل استعلامًا واحدًا بدلًا من ذلك.

‏**تشغيل التحكم.** بعد ترحيل الإضافات وإصلاحات النواة (التراجع عن سلاسل المالكين، ومسارات الأصول، و`unity.find`، وتنسيق الأرقام)، حلّ فهرس RQL ‏**60 / 60** مهمة بـ 23,274 رمز موجّه و3.4 استدعاء أداة و4.8 s لكل مهمة.

## نتائج عالم اللعبة التجريبي

يقيس مشروع RQL اللغة بمفردها، خارج Unity: عالم لعبة مولَّد ووكيل يستخدم إما RQL أو أدوات الانعكاس (reflection) البسيطة (`find_objects`، و`get_object` كتفريغ JSON، و`describe_type`، و`set_value`، و`call_method`). أنظف فحص استخدم 30 مهمة جديدة كُتبت بعد تجميد كل الضبط، وشُغّلت مرة واحدة، 3 مرات لكل مهمة.

## المنهجية

‏**محرر Unity.** القياس على Unity-MCP 0.93.4 (كل أداة مفعّلة، أداة واحدة لكل إجراء: `gameobject-*`، `assets-*`، `scene-*`، `object-*`، `console-get-logs`، `script-execute`، `tests-run`، …) مقابل فهرس RQL ‏(`rql-query`، `rql-mutate`، `rql-schema`، `script-execute`، `tests-run`، `screenshot-isolated`، `unity-tool-list`). أداة الاختبار والمشهد والنموذج نفسها لكليهما: `deepseek-flash`، مع إيقاف الاستدلال (reasoning)، و temperature 0. ‏20 مهمة × 3 تشغيلات، Unity 6000.6.4f1. حصلت كل حالة على الأدوات نفسها تمامًا التي يراها عميل MCP، بأسمائها وأوصافها ومخططات مدخلاتها، واستُدعيت عبر الإضافة. لا تنجح المهمة إلا إذا نجح فحصها ولم يتغير أي شيء آخر في المشهد.

‏**عالم اللعبة التجريبي.** المهام والمُقيِّم والنموذج والميزانيات نفسها لكلتا مجموعتي الأدوات؛ الأدوات وحدها تختلف. النموذج DeepSeek V4.1-Flash، بحد أقصى 12 خطوة لكل مهمة، و3 تشغيلات لكل مهمة. يحسب مُقيِّم مخفي الإجابة المتوقعة بشكل مستقل؛ وتفشل مهام التعديل عند أي تغيير غير مقصود. لم تُستخدم المهام المحجوزة للضبط قط؛ أما مجموعة المهام الثانية فكُتبت بعد تجميد الضبط وشُغّلت مرة واحدة.

## تحفظات

- ‏**عائلة نماذج واحدة.** استخدم كلا الاختبارين نماذج DeepSeek. قد تُظهر نماذج أخرى أرقامًا مختلفة.
- ‏**الإصدارات المقيسة.** تقارن أرقام محرر Unity بين Unity-MCP 0.93.4 وفهرس RQL على مشهد واحد وإصدار واحد من Unity؛ والأدوات والنماذج تتغير مع الوقت.
- ‏**عينات صغيرة.** 60 تشغيلًا لكل حالة في المحرر؛ ومن 81 إلى 90 تشغيلًا لكل حالة في نتائج عالم اللعبة التجريبي أعلاه.
- ‏**المؤلف نفسه.** صمّم مؤلف اللغة نفسه مهام RQL وعالم اللعبة التجريبي. المهام المحجوزة ومجموعة المهام المكتوبة بعد الضبط تقلل هذا الانحياز لكنها لا تزيله.
- ‏**التكلفة نسبة.** يجعل التخزين المؤقت للموجّهات (prompt caching) التكلفة تعتمد جزئيًا على حركة مرور أخرى؛ أعداد الرموز واستدعاءات الأدوات مؤشرات أكثر ثباتًا.
